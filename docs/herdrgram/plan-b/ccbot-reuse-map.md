Скрытые допущения, ломающиеся на herdr:
- session_map.json is tmux-shaped and tmux-produced. Keys are f"{TMUX_SESSION_NAME}:{@window_id}" (hook.py:220; consumed at session_monitor.py:402-407) and the writer needs $TMUX_PANE + `tmux display-message` (hook.py:191-207). Under herdr, $TMUX_PANE is unset, so ccbot's hook returns at hook.py:193 and the whole monitor watch-list would be permanently empty. herdr already solves this: its own SessionStart hook reports the Claude session id via pane.report_agent_session, readable through pane.get/agent.list (herdr-api-notes.md:21) — but `herdr integration install claude` rewrites ~/.claude/settings.json, so herdrgram must NOT install a competing hook there casually.
- Window ids are assumed stable-ish, with an explicit recovery path when they are not. tmux @ids change on tmux server restart, so ccbot re-resolves them by window NAME (session.py:223-373 resolve_stale_ids, plus session_map migration at session.py:485-525). herdr has the same hazard with a weaker fix: pane ids wC:pN are reused after close (herdr-api-notes.md:8) and there are no stable names to re-resolve against. herdrgram must treat pane_id as ephemeral routing info, pin identity to the Claude session_id (and terminal_id within a herdr uptime), and re-bind on pane_created/pane_agent_detected.
- One tmux window == one Claude session == one Telegram topic. herdr breaks this: a tab can hold several panes (pane.split), a pane can be a plain shell, and the user's live layout is one tab per session only by convention (herdr-api-notes.md:8). Binding must be per-PANE, and 'tab closed' is not a reliable session-ended signal — herdr-api-notes.md:47 observed pane_exited without tab_closed, so pane_exited is the primary lifecycle event.
- A project cwd identifies at most one interesting session. scan_projects filters candidate transcripts by the set of live tmux window cwds (session_monitor.py:143, 182); two Claude panes in the same repo are indistinguishable there and are only separated later by the active_session_ids gate (session_monitor.py:297). On herdr, multiple panes in one repo is normal — drop the cwd scan entirely and index by agent_session.value.
- The transcript path is derivable from cwd + session_id. session.py:748-761 encodes the cwd with re.sub(r'[^a-zA-Z0-9-]','-',cwd) — note this is stricter than the '/ -> -' shorthand in the notes (dots and underscores also become dashes). herdr exposes cwd AND foreground_cwd; the transcript dir is keyed by the cwd Claude was LAUNCHED in, so a shell `cd` inside the pane can desync foreground_cwd from the project dir. Keep the glob fallback `*/<session_id>.jsonl` (session.py:770-775) as the authoritative resolver.
- The JSONL file only ever grows. _read_new_lines only detects shrink (offset > size, session_monitor.py:212-220). An in-place rewrite of equal or larger size — compaction, transcript edits, a resumed session rewriting earlier lines — leaves the offset pointing into different content and silently replays or skips messages. There is no content checksum/anchor. Worth adding a cheap guard (e.g. store the byte length + last line uuid).
- /clear is only noticed because the tmux-keyed map changes value. Detection lives at session_monitor.py:444-453 (same window key, different session_id). herdr 0.7.1 has NO agent_session-changed event (event list, herdr-api-notes.md:36), so a purely event-driven herdrgram would miss /clear entirely and keep reading the dead transcript. Mitigation: poll agent.list on a slow cadence and/or re-read pane.get on every pane_agent_detected.
- The bot is never down while Claude is producing output. New sessions are initialised at EOF (session_monitor.py:303-319) and _cleanup_all_stale_sessions (session_monitor.py:415-432) deletes the persisted offset of any session missing from the map at startup — so if the map is momentarily empty (on herdr: socket not ready, herdr server restarting), the offset is wiped and the next cycle restarts at EOF, dropping everything produced meanwhile. This directly contradicts the herdrgram goal 'walk away and continue immediately in Telegram'. Fix: never delete offsets on a failed/empty snapshot; distinguish 'herdr unreachable' from 'session gone'.
- Polling cadence is free because tmux capture-pane is a local exec. The system runs three clocks: monitor 2.0s (config.py:86), status polling 1.0s (status_polling.py:45), topic probes 5.0s (status_polling.py:48), plus per-event bursts — interactive UI 0.3s sleep then capture (bot.py:1936-1945) and bash capture 2s + 30x1s (bot.py:915-921). On herdr each of those becomes a socket RPC against the server driving the user's live terminal. herdrgram should collapse them: events.subscribe for lifecycle/status, pane.wait_for_output for bash, and keep a slow reconcile poll only as a safety net.
- events.subscribe gives a clean slate. False on 0.7.1: it REPLAYS retained history (herdr-api-notes.md:39), so an event-driven port of _detect_and_cleanup_changes would see pane_created/pane_agent_detected for every existing pane at startup and could wipe or re-init offsets. All event handlers must be idempotent, and reconcile-from-snapshot must happen regardless of version (0.9.0 flips the behaviour the other way).
- pane.agent_status_changed can be subscribed globally. It cannot — on 0.7.1 it requires a pane_id (herdr-api-notes.md:38). Any herdrgram design that assumes 'one subscription tells me when any agent goes blocked' needs per-pane (re)subscription as panes appear, and must handle a stale pane_id in the subscription list (unverified whether it errors the whole subscription).
- Bash-mode (!cmd) output is not in the transcript. The parser deliberately discards <bash-input>/<bash-stdout>/<bash-stderr> (transcript_parser.py:148-150), so ccbot screen-scrapes the pane (bot.py:900-926 + terminal_parser.py:266-300, matching on the first 10 chars of the echoed command and on '─' chrome rules). That path survives on herdr via pane.read source='recent', but it is inherently lossy for long output (only the scrollback herdr returns) and depends on Claude's TUI chrome, which changes between Claude Code versions.
- Interactive prompts are detected from the transcript then confirmed by a screen scrape 0.3s later (bot.py:1936-1945). This is a race: the tool_use line lands in the JSONL before the TUI paints. herdr replaces the guess with a fact — agent_status 'blocked' plus agent.explain rules live_blocked_form / bash_permission_prompt / generic_permission_prompt / mcp_elicitation_prompt (herdr-api-notes.md:32) — so the sleep-and-hope should be replaced by an event/status wait.
- Message ordering across surfaces is guaranteed by the JSONL alone. The monitor emits strictly in file order per session, but the Telegram side interleaves status updates (status_polling), interactive UI messages and bash captures through a separate per-user queue (bot.py:1940-1942 queue.join()). Any herdr port that adds a second, faster event path (status_changed) must keep that queue as the single serialisation point or the topic will show tool results before the tool call.
- TrackedSession.file_path is authoritative. It is not — it is written once (session_monitor.py:313) and never read (reads always use session_info.file_path, session_monitor.py:338). Once the herdr port removes the filesystem rescan, this field silently becomes load-bearing and must be refreshed.
- Text-mode byte offsets are real byte offsets. _read_new_lines mixes f.seek(int) with f.tell() cookies on an aiofiles TextIOWrapper (session_monitor.py:208-253) and compares one decoded CHARACTER against '{' (l.230). It works only because the UTF-8 decoder state is clean at line boundaries; a multi-byte character straddling a resumed offset would misbehave. Binary mode removes the whole class of problem.
- mtime resolution is fine for a 2s poll. The skip test (session_monitor.py:330-335) requires BOTH mtime<=last AND size<=offset, so it degrades safely, but note _file_mtimes is in-memory only (l.86) while offsets persist — after every restart the first cycle stats and re-reads every tracked file.
- Topic liveness is probed out-of-band (status_polling.py:47-51: private-chat probe sends and deletes an invisible message, 5s supergroup probe). Not part of this subsystem, but it is the mechanism that decides whether monitor output has anywhere to land; it is Telegram-specific and carries over to herdrgram unchanged — the herdr side only changes what 'the session died' means (pane_exited instead of a missing tmux window).

Заметки: END-TO-END PATH TODAY (all line refs in ~/projects/misc/ccbot): Claude writes ~/.claude/projects/<encoded-cwd>/<session_id>.jsonl -> SessionMonitor._monitor_loop every 2.0s (session_monitor.py:481-521) calls session_manager.load_session_map() (l.499) and _detect_and_cleanup_changes() (l.502) to get {tmux window -> session_id} from ~/.ccbot/session_map.json written by ccbot's SessionStart hook (hook.py:251-266) -> check_for_updates (l.281) scans ~/.claude/projects filtered by live tmux cwds (scan_projects, l.104-194), stats each file, and reads only new bytes from the persisted offset (_read_new_lines, l.196-279) -> TranscriptParser.parse_entries in carry-over mode (l.351) pairs tool_use with tool_result across poll cycles via per-session _pending_tools (l.81, 350-358) -> NewMessage per ParsedEntry (l.366-377) -> bot.handle_new_message (bot.py:1915) -> session_manager.find_users_for_session (session.py:1057, in-memory window_states lookup, deliberately no file I/O) -> per-topic message queue.

SPLIT OF CONCERNS: the subsystem is already ~85% transport-agnostic. transcript_parser.py (776 lines) and monitor_state.py (109) have ZERO tmux references; session_monitor.py has exactly one tmux import (l.25) feeding four code regions (l.93-102, 104-194, 387-413, 434-479) plus the loop's session_manager sync (l.499). Test carry-over is similarly favourable: 741 of the 889 test lines (transcript parser + monitor state + integration) port unchanged, and the 148-line session-monitor test file only exercises _read_new_lines, which is kept.

WHAT HERDR MAKES STRICTLY BETTER: (1) agent.list replaces both the tmux window scan AND session_map.json AND ccbot's hook — one RPC returns pane_id, cwd, agent_status and agent_session.value (the Claude session UUID) for every agent pane; (2) pane_exited / pane_agent_detected events replace polling for lifecycle; (3) agent_status blocked/working/idle/done replaces the terminal_parser screen-scrape heuristics for 'is Claude waiting on me'; (4) pane.wait_for_output replaces the bash-capture busy loop; (5) notification.show + pane.report_metadata + agent.focus give the desk-side half of 'come back and continue right there' with no external terminal (ccbot's /show needed one).

WHAT HERDR DOES NOT GIVE (the parser stays essential): herdr exposes no transcript content and no transcript_path (herdr-api-notes.md:21) — pane.read returns rendered TUI text with chrome, wrapping and truncation, which is unusable for faithful Telegram rendering of thinking blocks, diffs, images and long tool output. So the JSONL tail-reading pipeline (monitor_state + _read_new_lines + parse_entries) remains the backbone of herdrgram; herdr only replaces the discovery/lifecycle layer. Both signals are needed, and they have different latencies: the JSONL lands after a block completes, herdr status flips as the TUI repaints. Design the merge point explicitly (e.g. status events drive polling cadence and 'blocked' UX; transcript drives content), otherwise the two will race and duplicate output.

DEPENDENCIES TO COPY ALONGSIDE: utils.atomic_write_json (utils.py:24-49), utils.read_cwd_from_jsonl (utils.py:52-72, only needed if the fallback scan is retained — otherwise droppable), session.py:748-761 _encode_cwd/_build_session_file_path and the glob fallback at session.py:770-775, config fields claude_projects_path / monitor_poll_interval / monitor_state_file / show_user_messages / show_tool_calls (config.py:71, 80-96), and the Telegram-side sentinel consumers markdown_v2.py:105 and handlers/response_builder.py:46 that decode the expandable-quote markers the parser emits. Скрытые допущения, ломающиеся на herdr:
- Window-id durability. ccbot assumes tmux window ids are unique and stable for the life of the tmux server, and papers over server restarts with a startup resolve_stale_ids() name-matching pass (.claude/rules/architecture.md). herdr pane ids wC:pN are REUSED after a pane closes (herdr-api-notes.md:8), so every _status_msg_info / _tool_msg_ids / merge comparison keyed on the id (message_queue.py:79, :121, :448, :507, :688) can bind to a different session with no detectable transition. Use terminal_id (term_<hex>, durable per PTY - verified on wC:p1) or an internal binding uuid.
- Capture-pane semantics. _check_and_send_status (message_queue.py:626) assumes a cheap synchronous capture of the visible pane whose text contains Claude's bottom chrome at tmux's geometry. herdr's equivalent is pane.read {source:'visible'|'detection'}: an async socket round-trip, wrapped to herdr's pane width, bottom-buffer-only for 'detection', and carrying a `truncated` flag. I verified parse_status_line's contract still holds against a real detection snapshot (separator line, prompt, status bar present), but the width difference means any column-sensitive parsing must be re-validated.
- Status is a scraped string, not a state. The typing indicator fires on the literal substring 'esc to interrupt' (message_queue.py:517, :577) and the status body is Claude's raw spinner line (terminal_parser.py:199-238, spinner glyphs frozenset). That string changes with every Claude Code release and carries volatile content (elapsed time, token counts), so the last_text dedup at :511 and :688 almost never hits while Claude is working - meaning the 1s poll produces roughly one edit_message_text per second per active topic, which is the real flood-control pressure the whole two-tier RetryAfter machinery exists to absorb. herdr's agent_status enum removes both the fragility and most of the traffic.
- Polling cadence is load-bearing. STATUS_POLL_INTERVAL = 1.0 (status_polling.py:45) and the 'skip enqueue while the queue is non-empty' guards (message_queue.py:619-620, status_polling.py:419) are the only backpressure. Switching to herdr's event stream inverts this: pane.agent_status_changed can burst (working->blocked->working within one tool call), so the port needs an explicit debounce/coalesce window, otherwise Telegram edit rate limits are hit harder than with polling.
- One extra capture per message. _check_and_send_status runs after EVERY content task (message_queue.py:427) and again after each tool_result edit (:366, :381). On tmux that was a local fork/exec; on herdr it is a socket RPC per message. Cache agent_status from the subscription instead.
- No post-conversion length check anywhere. response_builder splits at 3000 raw chars 'to leave room for MarkdownV2 expansion' (response_builder.py:80-83), but nothing re-measures after convert_markdown. MarkdownV2 escaping adds one backslash per special char (markdown_v2.py:111), so escape-dense text can more than double; send_with_fallback (message_sender.py:90) then sends >4096 and the plain-text fallback (:100) re-sends a body of the same original length and fails too, dropping the message with only a logger.error (:106). The 3000 figure is a guess, not a bound.
- split_message can return chunks longer than max_length when re-opening a code fence (telegram_sender.py:85, :98-106) - reproduced: 70 utf16 units for max_length=60. It also emits empty '```lang ... ```' chunks. Both are pre-existing ccbot bugs, not herdr-specific; fix them in the port.
- UTF-16 accounting is inconsistent across the pipeline. telegram_sender is scrupulously UTF-16-correct, but markdown_v2._render_expandable_quote budgets with len() (:121, :137-149) and response_builder truncates with len() (:40-41, :51-55, :81). Emoji/CJK-heavy thinking blocks can therefore exceed Telegram's real limit.
- All delivery state is process-local and non-persistent (_status_msg_info, _tool_msg_ids, _flood_until at message_queue.py:76-82). After a bot restart: orphan status messages stay forever in every topic (the safety-net delete at :568-575 only catches within-process cases), tool_use->tool_result pairing is lost so results arrive as new messages, and the flood ban is forgotten - which is exactly why ccbot pre-fills the AIORateLimiter bucket on restart (.claude/rules/message-handling.md). herdrgram inherits all of this unless the maps are persisted under a stable session key.
- A Telegram send failure is destructive. message_sender.py:72-74 -> session.py:928-930 kills the tmux window on 'Topic_id_invalid'/'Message thread not found'. Ported naively to herdr this becomes pane.close on a user's live desk pane triggered by a transient API error - directly against the project's hard rules. Gate it on bot-owned panes only.
- Thread_id is absent from the merge key (message_queue.py:121-122) and the merged task inherits first.thread_id (:194). Safe only under ccbot's 1 topic = 1 window = 1 session invariant; any herdr topology where that breaks (pane-id reuse, one pane observed by two topics, a topic following a session across pane recreation) causes cross-topic message delivery.
- Queue bookkeeping depends on asyncio.Queue internals. Скрытые допущения, ломающиеся на herdr:
- tmux window ids are stable within a server and only reset on tmux restart — that is the entire premise of resolve_stale_ids (session.py:223-373). herdr pane numbers are RECYCLED after close (~/.config/herdr/session.json: public_pane_numbers {1,2,3,5,7}, next_public_pane_number 12; the api-notes state numbers are reused). On this machine `herdr integration install claude` OVERWRITES that file, and herdr's hook is currently the ONLY SessionStart entry. Any herdrgram hook is one `herdr update` away from being deleted. Prefer zero hooks.
- Session end is assumed to be undetectable — there is no SessionEnd hook, so orphan entries are GC'd by scanning live tmux windows (session.py:498-526, 948-969) and by the status poller noticing find_window_by_id returns None (status_polling.py:327-354). herdr gives an explicit pane.exited event (verified, global scope); note that tab_closed was NOT observed when a tab closed because its last pane exited, so pane.exited must be the primary signal and a periodic agent.list reconcile the backstop.

- `config = Config()` (config.py:178) and `session_manager = SessionManager()` (session.py:1157) execute at import time, so importing either module requires TELEGRAM_BOT_TOKEN/ALLOWED_USERS and reads/writes the real state file. - find_users_for_session (session.py:1057-1074) is correct only because load_session_map() runs on every 2 s monitor tick (session_monitor.py:499); the docstring explicitly trades freshness for O(1). On herdr the refresh trigger changes from a timer to events, so if events are missed (subscription dropped, server restarted) the map silently goes stale and messages are delivered to the wrong topic or nowhere. A periodic agent.list reconcile is mandatory, not optional.
- 'The multiplexer server is always up' — main.py:313-315 creates the tmux session once and never rechecks. The herdr socket can vanish (server restart, `herdr update --handoff`), and after a restart every pane is a NEW PTY (terminal_id changes) even when pane ids and session ids are restored. herdrgram needs reconnect-with-backoff plus full re-reconcile, and must treat terminal_id changes as 'same Claude session, new process' rather than 'session ended'.

Заметки: Scale of the change: of the ~1750 lines in this subsystem, roughly 600 survive nearly untouched (transcript derivation + reading, Telegram chat-id routing, thread-binding CRUD, utils, most of Config), roughly 750 are deleted outright (the entire session_map.json mechanism: hook.py, and session.py L145-147/223-526/618-730/948-969), and roughly 150 are rewritten thin against the socket API.

Recommended herdrgram state model (replaces window_states + session_map):
  Binding = {topic: (chat_id, thread_id, user_id), session_id (Claude UUID — the durable key), pane_id (address, recyclable), terminal_id (PTY identity, detects restart), tab_id, cwd, label, offsets_by_user}
  Persisted in ~/.herdrgram/state.json via atomic_write_json. Resolution order at every use: session_id -> pane via agent.list; verify pane.agent_session.value still equals session_id before ANY send/close; if it does not, treat the pane as foreign and re-resolve. That single invariant is what replaces all of ccbot's stale-id machinery and is also what protects the user's live panes from a recycled pane number.

What herdr gives for free (delete ccbot code): pane->Claude session id (verified live on wC:p1/p2/p3/p5/p7), pane cwd, agent status without screen-scraping on our side, lifecycle events (pane.created/exited/agent_detected), durable session ids across herdr server restart via session.json + automatic `claude --resume`, pane/tab focus as a native /show, notification.show as a desktop-side signal, pane.report_agent_session to force a session id after resume, and pane.report_metadata to mark a pane as linked to a Telegram topic in the sidebar.

What herdr does NOT give (must stay in herdrgram): the transcript JSONL path — pane.get returns only agent_session{kind:'id',value}, so the cwd+session_id derivation plus the glob fallback remain load-bearing; the transcript CONTENT and the per-user byte offsets that drive unread detection; any notion of a Telegram topic; and durable identity for pane_id (numbers are recycled) or terminal_id (new PTY after every server restart) — only the Claude session UUID is durable, and even that changes on /clear.

Version risk to flag: everything above uses methods verified present on the installed 0.7.1 (agent.list, pane.get, pane.send_input, pane.send_keys, pane.report_agent_session, pane.report_metadata, tab.create/close/focus, agent.start, agent.focus, events.subscribe, notification.show). Two behaviours differ by version and the bridge must tolerate both: 0.7.1 replays retained events on subscribe while newer versions do not, and pane.agent_status_changed's payload has not yet been captured on this machine — verify it on a scratch tab (`herdr tab create --workspace wC --label herdrgram-probe --no-focus`, then `herdr tab close`) before finalizing the status pipeline.

Test-debt warning for the port: the parts of this subsystem that survive unchanged are precisely the parts with NO direct tests in ccbot — _encode_cwd, _build_session_file_path, _get_session_direct, get_recent_messages, list_sessions_for_directory, resolve_session_for_window, send_to_window, find_users_for_session, cleanup_dead_topic, and all of main.py. The 297-test suite concentrates on pure dict operations and on the migration code that herdrgram deletes. Budget for writing these tests fresh rather than assuming coverage travels with the code.

Скрытые допущения, ломающиеся на herdr:
- WINDOW IDS ARE STABLE AND UNIQUE-WHILE-ALIVE. tmux `@N` is monotonic per server and never reused; ccbot leans on that everywhere (bot.py:1121, 1653, callback_data payloads) and its only recovery path, session.py:223-260 `resolve_stale_ids`, re-maps stale ids BY WINDOW NAME after a tmux restart. herdr REUSES pane numbers after close (herdr-api-notes.md:8). Consequence: a persisted binding to `wC:p7` can silently resolve to a *different live session* after a close/open cycle — messages from Telegram land in the wrong agent. Bind on `agent_session.value` (Claude session UUID) + `terminal_id`; treat pane_id as a cache and re-verify it (`pane.get`) before every send.
- NAME-BASED RECOVERY IS SAFE. resolve_stale_ids matches on window name, and create_window guarantees uniqueness by appending `-2`, `-3` (tmux_manager.py:527-530). herdr tab labels have no uniqueness guarantee and the user renames tabs freely, so name-matching will mis-bind two tabs for the same project. Recovery must match on session UUID + cwd only.
- `; exit` MAKES DEATH PERMANENT. tmux_manager.py:549-558 launches `claude; exit` so the window vanishes when Claude exits, and the whole symmetric lifecycle (topic auto-delete, stale-binding scan) is built on 'window gone == session over'. On herdr the opposite is true: a server restart RESTORES panes and auto-runs `claude --resume <id>` for any pane with a stored `agent_session` (herdr-api-notes.md:73). A session the bot 'killed' can come back, re-detect as an orphan, and get a fresh auto-created topic. Killing must also clear the stored agent_session / close the tab, and the orphan scanner must remember what it deliberately killed.
- session_map.json IS THE BOT'S OWN CHANNEL. Keys are `"<tmux_session>:<window_id>"` (session.py:466, 630, 964) written by ccbot's OWN Claude SessionStart hook (src/ccbot/hook.py), and _create_and_bind_window blocks 5 s (15 s for --resume) waiting for it (bot.py:1229-1235). herdr ships its own SessionStart hook (`~/.claude/hooks/herdr-agent-state.sh`, integration v7) and `herdr integration install claude` OVERWRITES ~/.claude/settings.json (herdr-api-notes.md:50). Installing a second SessionStart hook naively will be silently wiped on the next herdr update; and it is unnecessary, since `pane.get.agent_session` already carries the id. Drop session_map.json entirely.
- THE BOT OWNS ITS UNIVERSE. Every 'list what's out there' path is scoped to one tmux session named by config (bot.py:1071 list_windows, status_polling.py:184 orphan scan). herdr has no such namespace: `agent.list` returns ALL live claude panes, including the user's five personal ones (wC:p1/p2/p3/p5/p7). Without an explicit ownership marker the window picker offers to hijack the user's real sessions, and CCBOT_AUTO_CREATE_TOPICS-style scanning would create Telegram topics for every pane the user has open and later kill them on topic close. Needs a dedicated workspace or a `pane.report_metadata` ownership token, plus opt-in adoption.
- CAPTURE-PANE SEMANTICS. `tmux capture-pane -p [-e]` returns exactly the visible pane, unwrapped-as-displayed, no scrollback, with tmux's ANSI dialect (tmux_manager.py:190-229). Three consumers depend on that framing: is_interactive_ui (bot.py:1163), extract_bash_output diffing (bot.py:926), parse_usage_output (bot.py:499), plus the PNG renderer. herdr `pane.read` offers four different sources (visible / recent / recent-unwrapped / detection) with its own trimming and a `truncated` flag; none is byte-identical to tmux. Every terminal_parser regex and the screenshot renderer must be re-validated against real herdr reads before they are trusted.
- SCREEN SCRAPING IS THE ONLY STATUS SOURCE, AT 1 Hz. STATUS_POLL_INTERVAL = 1.0 s (status_polling.py:45) drives status messages, interactive-UI detection, the 10 s orphan scan and the 60 s topic probe. herdr provides `agent_status` (idle/working/blocked/done/unknown) as events, but `pane.agent_status_changed` is PER-PANE-ONLY on 0.7.1 (herdr-api-notes.md:38) — subscriptions must be opened/closed as panes come and go, and a stale pane_id in the list may error the whole subscription (unverified; probe it). Additionally 0.7.1 REPLAYS retained history on subscribe (herdr-api-notes.md:39) while 0.9.0 does not, so all event handlers must be idempotent and startup must reconcile from `agent.list`/`pane.list` on both versions.
- TEXT + ENTER IS TWO OPERATIONS WITH A HAND-TUNED GAP. tmux_manager.py:249-302: literal text, sleep 0.5 s, then Enter, because Claude's TUI treats a same-batch Enter as a newline; plus a special path that sends '!' alone, sleeps 1.0 s, then the rest, to enter bash mode. These are Claude-TUI quirks and must survive the port. But herdr `pane.send_input` accepts multi-line text typed LITERALLY (herdr-api-notes.md:24) — a Telegram message containing newlines may submit early, splitting one user message into several prompts. Must be probed on a scratch pane; `agent.prompt` (>=0.9) solves it properly and also refuses to send when the agent is already blocked.
- A KILLED TOPIC MEANS A KILLED SESSION. topic_closed_handler (bot.py:589) and /kill (bot.py:410) destroy the running agent. That was defensible when the window was bot-created; on herdr the same topic may be bound to a pane the user is sitting in front of. Closing a Telegram topic must not kill a pane the bot did not create — gate destruction on the ownership marker, and prefer 'unbind' as the default for adopted panes.
- /show ASSUMES A GUI ON THE BOT'S HOST AND A HARMLESS SECOND CLIENT. bot.py:277-297 checks DISPLAY/WAYLAND_DISPLAY and shells out to a terminal emulator; tmux_manager.py:374-435 builds a throwaway grouped session specifically so attaching does NOT yank other clients' views. herdr's `agent.focus`/`tab.focus` has no such isolation — it moves the desktop user's actual view. The ccbot design intent ('don't disturb the desk') must be re-expressed as: focus only on explicit request, otherwise `notification.show` a toast.
- CALLBACK_DATA IS SMALL AND TRUNCATION IS FREE. Six sites do `f"...{window_id}"[:64]` (bot.py:546, 557; history.py:48, 63). With `@5` there is headroom; with a 36-char session UUID the history payload `hp:<page>:<id>:<start>:<end>` overflows and truncates mid-number, silently paging to a wrong byte range. herdr pane ids (`wC:p1`) are short enough, but pane ids are exactly what must NOT be persisted in a button. Use a short opaque token and assert the 64-byte budget instead of slicing.
- THE JSONL PATH IS DERIVABLE FROM THE CURRENT CWD. resolve_session_for_window -> `~/.claude/projects/<cwd with / -> ->/<session_id>.jsonl` (session.py:748-762). herdr does not expose transcript_path (herdr-api-notes.md:21) and `pane.get` returns both `cwd` and `foreground_cwd`, which drift as the user cds inside the pane; Claude's project dir is fixed at session start. Store the cwd captured at bind time, or locate the JSONL by scanning ~/.claude/projects for the session UUID.
- SESSION ID IS STABLE FOR THE LIFE OF THE BINDING. handle_new_message routes purely by `msg.session_id` (bot.py:1928) and only /clear-via-Telegram clears the association (bot.py:701-703). The id also changes when the user types /clear AT THE DESK, which ccbot could not see; on herdr the same happens and `agent_session` updates under the bot's feet. Re-read `pane.get` on `pane.agent_detected` and on status transitions, and update the binding's session UUID (this is also the /clear handling — the explicit clear_window_session special case can then be deleted).
- PER-USER user_data IS AN ADEQUATE PLACE FOR PER-TOPIC PICKER STATE. bot.py:1009-1056 needs three near-identical '_pending_thread_id mismatch -> clear stale state' guards precisely because one user browsing in two topics collides. Any concurrent onboarding in two topics still races on `_selected_path` (bot.py:1526, 1578, 1605). Key picker state by thread_id in herdrgram.
- TELEGRAM TOPIC LIVENESS NEEDS ACTIVE PROBING, AND PRIVATE CHATS LIE. status_polling.py:47-55, 282-323: supergroups are probed silently every 60 s via unpin_all_forum_topic_messages, but private chats return ok=true for arbitrary thread_ids, so the bot sends an invisible zero-width message and immediately deletes it; send-failure paths also trigger session.cleanup_dead_topic (session.py:909-946), which KILLS THE WINDOW. This is Telegram-side, unchanged by herdr — but it means a transient Telegram error can destroy a live agent. On herdr, make dead-topic cleanup unbind-only by default.
- forum_topic_edited WITH name=None MEANS ICON-ONLY. bot.py:626-629 returns early; easy to lose in a rewrite and it would rename tabs to 'None'.
- THREAD_ID 1 IS NOT A TOPIC. `_get_thread_id` maps both None and 1 to None (bot.py:174) because 1 is the General topic. Transport-agnostic, must be preserved verbatim.

Заметки: IDENTITY IS THE WHOLE PORT. ccbot's bot layer is ~2700 lines of which the genuinely tmux-specific logic is small (capture, send_keys, kill/rename/create, the /show terminal launcher) but the tmux *identity type* — the string `@N` — is threaded through every handler, every callback payload, every persisted structure and every test. Define one `Binding` (telegram user_id + thread_id + chat_id <-> claude session UUID + cwd + terminal_id + cached pane_id + owned_by_bot flag) and one `resolve(binding) -> PaneRef | None`, and roughly 22 call sites collapse into one. Interestingly, the OUTBOUND direction (handle_new_message, bot.py:1928) is already keyed by Claude session id — it is herdr-native today and needs no change.

CONTROL FLOW INVERTS. ccbot polls tmux at 1 Hz for everything (status, interactive UI, orphan windows, dead windows). herdr pushes: `pane.created` / `pane.exited` / `pane.agent_detected` globally, `pane.agent_status_changed` per pane. Budget real work for the subscription manager: one long-lived connection for global events, per-pane (re)subscription as panes appear, reconnect-with-reconcile (`agent.list` + `pane.list`) on socket drop, and strict idempotency because 0.7.1 replays retained history on subscribe while 0.9.0 does not. Only the Telegram-side timers (60 s topic probe, private-chat probe) stay time-based.

FOUR CCBOT CONCERNS DISAPPEAR ENTIRELY: (1) session_map.json + the custom SessionStart hook + wait_for_session_map_entry + the resume-override fix-up (bot.py:1229-1272) — herdr's `agent_session` replaces all of it, and installing a competing hook is actively unsafe because `herdr integration install claude` overwrites settings.json; (2) the `; exit` shell wrapper and the whole 'window disappeared' inference — `pane.exited` is the signal; (3) `make_view_session` / `select_window` / terminal-emulator spawning / DISPLAY checks — `agent.focus` is one call; (4) `resolve_stale_ids`' name-based remapping — replaced by session-UUID reconciliation.

THREE CONCERNS GET HARDER, NOT EASIER. (a) OWNERSHIP: tmux gave ccbot a private namespace (its own session); herdr is shared with the user's real work, so herdrgram needs an explicit ownership marker before any list/adopt/kill flow is safe — this is the single highest-risk design decision in the port, and it must default to non-destructive. (b) RESURRECTION: herdr restores agent panes and auto-resumes them after a server restart, so 'killed' is not final unless the stored agent_session is cleared. (c) FOCUS ETIQUETTE: focusing a pane changes what the person at the desk is looking at; ccbot's view-session hack existed precisely to avoid that, and the intent must be preserved as 'toast by default, focus on request'.

WHAT HERDR MAKES POSSIBLE THAT CCBOT COULD NOT DO (worth designing for now, not retrofitting): `agent_status` transitions give free, maintained 'working / blocked / done' status without screen scraping, so the status message and the blocked-prompt notification become event-driven and instant; `agent.list` gives a genuine cross-session overview command (/panes) with per-session status; `notification.show` gives a desktop-side signal when a Telegram message arrives, which is the missing half of 'send messages from either side interchangeably'; `pane.report_metadata` puts '📱 topic N' in the herdr sidebar so the desk side can see the link; `agent.explain` makes blocked-state debugging tractable. On >=0.9, `agent.prompt {prompt, wait:{until}}` replaces the hand-tuned send_input/0.5 s/Enter dance and refuses to send into a blocked agent — a correctness win, flagged as a newer-version dependency.

TEST REALITY CHECK. Of the 297 passing ccbot tests, this subsystem owns 25: 16 for three bot.py commands (/show, forward, /kill) and 9 for transcribe.py. directory_browser.py, history.py and cleanup.py have ZERO direct tests; text_handler, callback_handler, photo/voice handlers, bash capture, handle_new_message, onboarding and lifecycle have ZERO. So 'port the tests' buys almost nothing — the port should instead reuse the *fixture style* (_make_update/_make_context in conftest.py) and the *error-path matrix* (unbound / dead / unauthorized / stale-callback-from-another-topic) applied uniformly across all handlers, plus a fake herdr socket server (newline-delimited JSON over a temp unix socket) so the client, the subscription manager and the reconcile logic get real integration coverage — that is where the actual risk lives, and it is exactly what libtmux mocking never covered in ccbot.
