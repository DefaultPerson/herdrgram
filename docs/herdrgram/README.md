# herdrgram

Telegram ⇄ Claude Code over **herdr**, without tmux: step away from the desk and carry on with the same session from Telegram, come back and carry on in herdr, type from either side.

> `DECISION.md`, `PLAN-adopt-ccgram.md`, `research/` and `plan-b/` are the original Russian planning notes, kept as they were written. This file is the English runbook and is the only one of them that is maintained.

Status (2026-09-13): running as a test stand. The patches listed below are live on this fork and are the material for upstream pull requests.

## What this fork is

This repo is `alexei-led/ccgram` v4.10.3 plus the herdrgram patches — `git log upstream/main..main` lists them, and the remote `upstream` points at ccgram.

The planning history behind it:

- `DECISION.md` — the conclusion: a working bridge already exists (`alexei-led/ccgram`, herdr backend, MIT), so adopt it with a small fork instead of rewriting ccbot.
- `PLAN-adopt-ccgram.md` — the adoption plan: trial run → fork → pull requests upstream.
- `research/` — verified facts about the herdr 0.7.1 API, notes on its socket API, a survey of existing projects, and a gap analysis of ccgram.
- `plan-b/` — groundwork for a from-scratch implementation in case ccgram had not fitted: a reuse map of the ccbot modules. The from-scratch design and plan were never finished; that workflow stopped after the pivot to ccgram and can be resumed (see `plan-b/README.md`).

## Running the test stand (2026-09-13)

- **Config**: `~/.ccgram/.env` — the token for a bot of your own (`<your bot>`, a dedicated test bot rather than the one your main install polls; two pollers on one token trade 409s on `getUpdates`), `CCGRAM_MULTIPLEXER=herdr`, the patch flags enabled, `AUTOCLOSE_DONE_MINUTES=0`, `AUTOCLOSE_DEAD_MINUTES=2`.
- **Claude Code hooks**: `uv run ccgram hook --install` has already been run — nine events installed alongside the herdr hook. Check with `uv run ccgram doctor`, undo with `uv run ccgram hook --uninstall`.
- **Process**: the systemd user unit `~/.config/systemd/user/ccgram.service` (`ExecStart=.venv/bin/ccgram`, `WorkingDirectory=` this repo, `Restart=on-failure`). Use `systemctl --user status|restart|stop ccgram`, and `journalctl --user -u ccgram -f -o cat` for logs. After changing code: `systemctl --user restart ccgram`.
- **Hiding a session from the bot**: `herdr tab rename <tab_id> __name__`. Bring it back with `herdr tab rename <tab_id> name`.

## Patches on top of upstream

- `CCGRAM_KILL_ON_TOPIC_CLOSE` — closing or deleting a topic kills the herdr pane. Upstream never kills a session that was started by hand.
- `CCGRAM_DELETE_TOPIC_ON_AUTOCLOSE` — autoclosing a dead topic deletes it instead of closing it.
- `/show` and the `show` toolbar button — focus the session's pane in herdr (`herdr agent focus`, falling back to `tab focus`).
- `CCGRAM_ECHO_USER_MESSAGES=false` — do not echo into Telegram what was typed in the terminal.
- `CCGRAM_HERDR_NOTIFY_ON_INJECT` — a herdr toast, "Telegram → <session>", when a message from Telegram is delivered.
- `CCGRAM_TOPIC_NAME_DECORATIONS=false` — the topic name is the plain name: no status emoji, no RC/YOLO badges, and a state change no longer renames the topic. A rename arrives only when the name itself changes, that is, when the herdr tab is renamed.
- `CCGRAM_TOPIC_RANDOM_ICON` — every topic ccgram creates gets a random icon from Telegram's forum icon set (`getForumTopicIconStickers`, 112 of them) and a random colour out of the six allowed. Icons try not to repeat within a chat, and where a chat refuses a custom icon (a private chat) the colour alone remains.
- `CCGRAM_MUX_RENAME_FROM_TELEGRAM=false` — renaming a topic in Telegram is not pushed to herdr, where `tab rename` would relabel the tab for every neighbouring pane. Names flow herdr → Telegram only, and nothing is remembered locally: a name typed in Telegram lives until the tab label next changes.
- `CCGRAM_HERDR_TOPIC_LABEL=tab` — the topic name is the herdr tab label as it stands, bare number included for an unnamed tab. ` ▸ <pane>` is appended only where one tab holds several agents.
- `CCGRAM_TOPIC_ON_DEMAND` — a new session no longer creates a topic by itself. One message lands in General, "🆕 New session: `<name>` / 📁 `<cwd>` / 🤖 `<provider>`", with the buttons [🧵 Open topic] [🙈 Hide]. Opening creates the topic through the ordinary path: same random icon, same name, same binding, same history replay (see the next entry). There is one offer per window, it survives a bot restart, and if the window dies it turns into "⛔ Session ended: `<name>`" and is forgotten. Hiding deletes the message and remembers the window for good, though it can still be bound through `/sessions` and the `/new` picker. Pressing Open twice, or a second person pressing it, does not create a second topic. State lives in `~/.ccgram/topic_announcements.json`.
- `CCGRAM_TOPIC_BACKFILL_MESSAGES` (default 0 = upstream, nothing is replayed) — how many of the last transcript messages to show in a freshly bound topic. At `=10` every topic ccgram binds opens with the header "⏮ N messages in this session, M skipped — last K below" (or "⏮ Full history loaded: N messages" when everything fitted; a silent session gets no header at all), then K messages in order in `/history` format (👤 on user turns, tool calls collapsed). It covers every first-bind path: automatic topic creation on discovery, topic recreation through `/sync` after a delete, Open topic from an offer, and picking a window in `/new`. It deliberately does not cover resuming a session into a topic that was already showing the previous one (the dead-window banner, `/resume`), where the history is already on screen and part of it would be duplicated. Before reading, the transcript is marked delivered up to its current end and the replay is bounded by that same mark, so the live stream continues exactly from there: nothing is duplicated and "Jump to live" never pops up. Sending goes through the usual throttle, so ten messages take about ten seconds.
- `CCGRAM_HERDR_REQUIRE_NATIVE_SESSION` — fixes two tabs for one new Claude session. herdr first publishes a record without `agent_session` (ccgram derives a stand-in identity from the terminal id) and two or three seconds later the real one. Their targets differ, so upstream managed to create a topic for the stand-in and then a second one for the real session, and the first died and autoclosed. With the flag the stand-in record becomes `topic_eligible=False`: it is neither adopted nor announced, but it stays in the full listing, so liveness and cleanup still see it and no already-bound topic is counted dead. The cost is that a new session appears a couple of seconds later.
- `CCGRAM_WHISPER_PROVIDER=local` (new provider) — voice input transcribed on this machine by faster-whisper, no API key and no audio leaving the host. Record a voice note in a topic and the bot answers with the text and three buttons: Send to agent, Re-record (drops the text *and* the voice note, so the next take is the only one in the topic) and Close (drops the text, keeps the note). A placeholder message goes out first and becomes the result in place, because a CPU decode outlives Telegram's typing indicator. Defaults: `large-v3-turbo` at int8 on all cores but one, beam 5, language auto-detected; override with `CCGRAM_WHISPER_MODEL`, `CCGRAM_WHISPER_DEVICE`, `CCGRAM_WHISPER_COMPUTE_TYPE`, `CCGRAM_WHISPER_THREADS`, `CCGRAM_WHISPER_BEAM_SIZE`, `CCGRAM_WHISPER_LANGUAGE`. Measured on a 4-core i5-6400 with no GPU against 7.8 s of Russian speech: turbo takes 9.2 s (1.2x the recording) and reads it back verbatim, `Systran/faster-whisper-small` takes 2.8 s (0.4x) and drops a word here and there, `faster-whisper-base` takes 1.0 s and mishears short words outright. The weights (~1.5 GB for turbo) load once per bot process, on the first voice message, in a worker thread; decodes are serialized so two notes cannot take every core at once. `faster-whisper` is an optional dependency (`uv pip install faster-whisper`); without it the provider reports the install command.
- `/close` (no flag, new command) — retires a topic in Telegram without ending the session: it drops the binding first, so the `forum_topic_closed` update it triggers finds nothing to kill even under `CCGRAM_KILL_ON_TOPIC_CLOSE`, then closes the topic. In a private chat with topics Telegram answers "the chat is not a supergroup forum" to both `closeForumTopic` and `reopenForumTopic`, so there the topic is deleted instead — the only removal that surface offers — and the note says which of the two happened. The note goes to General, because a deleted topic takes any reply in it with it. Streaming stops at the unbind, and discovery offers the still-live window again in General within a poll cycle (`CCGRAM_TOPIC_ON_DEMAND`), or re-creates a topic for it when that flag is off. `/unbind` remains the non-destructive half: same release, topic untouched.
- `CCGRAM_IGNORED_THREAD_IDS` (default empty = upstream) — comma-separated topic ids ccgram must leave alone. Every update from those threads (text, commands, callbacks, media, topic closed/edited events) is dropped by a `TypeHandler` in an early handler group before anything else runs, so writing there never opens the window picker, and the topic is never bound, renamed, closed or deleted. Meant for a topic in the same chat that another producer sharing the bot token owns — for example a GitHub webhook relay posting into a pinned "GitHub" topic. The bot never receives its own messages as updates, so the relay's posts are invisible to ccgram either way; the flag guards against the user's replies in that topic.
- `CCGRAM_HERDR_NATIVE_STATUS_AUTHORITY` — herdr decides a pane's status, not the screen scrape. Upstream parses the terminal first and asks the backend only when it found nothing, so any line that looks like a spinner outvotes the one component that actually knows the state: Claude Code leaves the spinner glyph on the finished-turn line (`✻ Sautéed for 2m 26s · done 11:06 AM · 1 shell still running`), ccgram read it as "working", and the topic typed forever — an endless `sendChatAction` every four seconds, a stuck status bubble and a green emoji on an idle session. With the flag: `idle`/`done` means no status at all (the ordinary transition to idle runs), `working` takes its label from the screen and otherwise from herdr, `blocked` takes the interactive prompt from the screen (AskUserQuestion and permission keyboards keep working) and otherwise shows a "waiting for input" bubble, and `unknown` or no answer falls back to the old order. The screen is scraped either way: remote-control detection, vim insert mode and the passive shell relay all live on it. On tmux the flag changes nothing.
- Status-line parser (no flag, upstream material) — a spinner line carrying the finished-turn marker `· done` is no longer treated as a working status. With Claude Code ≥ 2.1 that line reads `<glyph> <Verb> for <time> · done <time>`, plus the tails `· N shell(s) still running` and `· N background agent(s)`. The exception is a line with `esc to interrupt`: only a live turn can be interrupted. Having found such a line the scanner stops instead of walking further up the scrollback, where an older spinner would resurrect the same bug. The second source of that bug is the update banner `✔ Update installed · Restart to update`, which Claude parks on exactly the status row and keeps there until a restart: the check mark (U+2714) is category So, and the `is_likely_spinner` heuristic took it for a spinner. The check-mark and ticked-checkbox family (`✔ ✓ ✅ ☑ ☒`) is now excluded by name, and the banner text is matched by its words too, so it survives both a glyph change and a rewording.
- Seeding session_map from herdr's native session id (no flag) — `herdr agent list` publishes Claude's own session id for each pane. ccgram derives the transcript path `~/.claude/projects/<cwd with '/' → '-'>/<id>.jsonl` from the (id, cwd) pair and, if the file exists, registers the session the way hookless providers are registered. This cures sessions started before the hook was installed, or with a broken hook: they used to get a topic but not a single line of output. Reading starts at the end of the file, so no history is replayed. Seeding runs when a topic is adopted and on every tick; once a session is tracked, the path never touches the disk.

## Known issues

- Sessions started before the hook was installed are now picked up by the native-id seeding described above. On upstream with tmux they stay unmonitored, because only a SessionStart event writes to session_map.
- `CCGRAM_TOPIC_ON_DEMAND` and `CCGRAM_HERDR_REQUIRE_NATIVE_SESSION` belong together: without the second flag the two-identity race would produce not two topics but two offers in General.
- Topics in a private chat are only created once the chat has been "seen": create any topic in the chat with the bot and write something in it.
